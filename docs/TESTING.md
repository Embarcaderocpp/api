# Проверки, которые нужно написать

В каркасе есть только `SystemStatusTest`: он проверяет запуск и технический endpoint.
Ни одного готового теста банковской логики нет. Таблицы ниже — задания,
а не уже выполненные автоматические проверки. Пиши тесты по мере реализации этапов.

## Разделение проверок

- Unit-тест: бизнес-правила сервиса, небольшой сценарий без Spring-контекста.
- HTTP-тест: валидация DTO, коды ответа, JSON и права доступа.
- Интеграционный тест: реальные PostgreSQL, миграции, транзакции и блокировки.

Для интеграционных тестов подключи Testcontainers и PostgreSQL той же основной версии,
что используешь локально. Потребуется Docker-совместимое окружение.
Не подменяй проверки SQL и блокировок тестами на H2 или моками репозиториев.

После подключения JPA старый тест контекста тоже потребует тестовую БД/настройки.
Настрой их осознанно; не отключай проверку миграций ради зелёной сборки.
Если назовёшь интеграционные тесты `*IT`, подключи Maven Failsafe и убедись,
что они действительно выполняются командой `verify`. Surefire обычно ищет `*Test`.

## Пользователи и счета

| ID | Сценарий | Что проверить |
| --- | --- | --- |
| A01 | Валидная регистрация | Профиль сохранён; пароль хеширован и не попадает в ответ |
| A02 | Две регистрации одного email, в том числе параллельно | Только одна запись; контролируемый конфликт |
| A03 | Запрос без входа / с неправильным паролем | `401`, а не `500` |
| A04 | Клиент A читает/закрывает счёт B | `404`, чужие данные не раскрыты |
| A05 | Открытие нового счёта | Владелец из Security, баланс ноль, номер уникален |
| A06 | Закрытие непустого или заблокированного счёта | Отказ, состояние не изменилось |
| A07 | Клиент вызывает административный маршрут | `403`; администратор может менять допустимые статусы |
| A08 | Регистрация с попыткой передать роль ADMIN | Административные права не получены |

## Переводы

Базовая фикстура: активные счета A = 1000.00 RUB, B = 200.00 RUB.
В каждом тесте независимые данные; не полагайся на порядок запуска тестов.

| ID | Сценарий | Что проверить после завершения транзакций |
| --- | --- | --- |
| T01 | A → B, 300.00 | A = 700.00, B = 500.00, ровно один успешный перевод |
| T02 | A → B, 1000.01 | Отказ; оба остатка прежние, успешной операции нет |
| T03 | 0, отрицательная сумма, 0.001, неизвестная валюта | Отказ, ни одна запись денег не изменилась |
| T04 | Чужой счёт списания / тот же счёт / заблокированный участник | Корректный отказ, оба остатка прежние |
| T05 | Сбой после начала изменений, до завершения перевода | Полный rollback балансов и всех связанных записей |
| T06 | Два одновременных перевода по 800.00 с A на B | Один успех, один отказ; A = 200.00, B = 1000.00 |
| T07 | Одновременные A → B на 100.00 и B → A на 100.00 | При успешных обоих исходные балансы; нет зависания, потерь и частичного коммита |
| T08 | Перевод одновременно с блокировкой/закрытием | Результат соответствует допустимому последовательному порядку операций |

Для T05 выбери контролируемый сбой в тестовом окружении. Не создавай публичный
параметр API «сломать перевод». Докажи, что сбой произошёл после начала изменений.

Для T06–T08 запросы должны выполняться в разных потоках и транзакциях.
Используй механизм синхронизации старта и таймауты, а не только `Thread.sleep`.
Проверь результаты обоих вызовов и итоговую БД из новой транзакции.
Не накрывай весь конкурентный тест одной тестовой транзакцией: фикстуры должны быть
закоммичены и видимы обоим участникам. При deadlock нужен описанный контролируемый
исход/повтор, а не зависание или потеря денег.

## Идемпотентность

| ID | Сценарий | Что проверить |
| --- | --- | --- |
| I01 | Два одинаковых запроса с одним ключом | Тот же ответ и id; одно списание |
| I02 | Один ключ, другая сумма/получатель | `409`, второго движения нет |
| I03 | Два конкурентных одинаковых запроса с одним ключом | Ровно одна операция; после завершения повтор возвращает её результат |
| I04 | Перезапуск приложения между запросами | Результат сохранён, повторного списания нет |
| I05 | Одинаковый ключ у двух пользователей | Независимые запросы, чужой ответ не возвращается |

## Журнал и выписки

| ID | Сценарий | Что проверить |
| --- | --- | --- |
| L01 | Успешный внутренний перевод | Связанные движения отражают оба счёта; сумма равна нулю |
| L02 | Сбой записи журнала | Нет ни нового перевода, ни изменения балансов, ни частичного журнала |
| L03 | Начальное финансирование и несколько переводов | Остатки всех клиентских счетов сверяются с журналом |
| L04 | Несколько страниц, одинаковые времена, границы периода | В статичном наборе нет пропусков/дублей; фильтр и права соблюдены |

## Как считать этап завершённым

Тест должен падать при нарушении конкретного бизнес-правила.
Проверка только HTTP `200` не доказывает правильность денег.
Сохрани команды запуска тестов в README и проверь, что CI не пропускает интеграционные тесты.
