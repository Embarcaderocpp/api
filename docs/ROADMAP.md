# Дорожная карта

Чекбоксы отмечаешь сам после проверки результата. Готовых сервисов и SQL нет.
Каждый этап включает код, тесты и краткое объяснение своих решений.

## Этап 0. Разобраться с каркасом

- [ ] Запустить `mvnw.cmd verify` и приложение.
- [ ] Выполнить запрос из `http/bank-lab.http`.
- [ ] Найти, где Spring создаёт контекст и почему обнаруживает контроллер.
- [ ] Объяснить разницу между HTTP JSON, DTO, сервисом и сущностью.

Готово, когда можешь пройти путь запроса от URL до Java-метода и обратно.

## Этап 1. PostgreSQL и собственная схема

- [ ] Заполнить первую часть `DATABASE.md`, нарисовать ER-диаграмму.
- [ ] Поднять PostgreSQL локально или написать `infra/compose.yml`.
- [ ] Найти и добавить зависимости JPA, драйвера PostgreSQL, Flyway и его PostgreSQL-модуля.
- [ ] Настроить подключение через окружение. Не коммитить пароли.
- [ ] Написать SQL-миграции для первых сущностей, ограничений и индексов.
- [ ] Написать JPA-сущности и репозитории; включить проверку схемы вместо её автогенерации.
- [ ] Научиться подключаться SQL-клиентом и проверять данные без приложения.
- [ ] Проверить миграции на совершенно пустой БД и при повторном старте.

Готово, когда чистая БД создаётся миграциями, данные сохраняются после перезапуска,
а неверные данные отклоняются не только Java-кодом, но и нужными ограничениями БД.
Таблицы переводов и журнала можно добавлять позже отдельными миграциями.

## Этап 2. Пользователь, клиент и доступ

- [ ] Создать DTO регистрации, сервис, репозиторий и контроллер.
- [ ] Валидировать email и пароль; обрабатывать конфликт уникальности.
- [ ] Подключить Spring Security и безопасное хеширование паролей.
- [ ] Для первого варианта реализовать HTTP Basic с пользователями из БД.
- [ ] Настроить текущего пользователя и роли; предусмотреть локального администратора.
- [ ] Оставить публичными регистрацию и технический статус, остальные маршруты защитить.
- [ ] Реализовать `GET /api/v1/me`; не отдавать JPA-сущность напрямую.
- [ ] Продумать CSRF для выбранного клиента и способа аутентификации; записать решение.
- [ ] Написать проверки регистрации, неверного пароля и прав доступа.

Готово, когда роль нельзя подменить телом запроса, пароль не возвращается клиенту,
а после перезапуска пользователь может пройти аутентификацию.
JWT и отдельный `/login` — дополнительное задание после основной части.
HTTP Basic здесь используется локально; для удалённого размещения потребуется HTTPS.

## Этап 3. Счета и бизнес-правила

- [ ] Спроектировать DTO и сигнатуры `AccountService`.
- [ ] Реализовать открытие, список, чтение, закрытие, блокировку и разблокировку.
- [ ] Проверять владение ресурсом, а не только факт входа.
- [ ] Добавить общий обработчик исключений и формат ошибок из `API.md`.
- [ ] Обработать гонку генерации одинакового номера счёта.
- [ ] Проверить статусы и невозможные переходы тестами.

Готово, когда два клиента не могут читать/изменять чужие счета, а закрытие счёта
с ненулевым балансом запрещено. В контроллере нет логики работы с балансом.

## Этап 4. Первый корректный перевод

- [ ] Спроектировать хранение перевода и добавить миграцию.
- [ ] Создать `TransferService`, DTO, контроллер и запросы к БД.
- [ ] Реализовать валидацию суммы, валюты, владельца и состояния счетов.
- [ ] Выбрать границу транзакции и объяснить поведение rollback.
- [ ] Выбрать способ защиты от одновременных списаний; реализовать его.
- [ ] Создать тестовые данные с балансами 1000.00 и 200.00.
- [ ] Выполнить перевод 300.00 и получить 700.00 и 500.00.
- [ ] Проверить недостаток средств, сбой посередине и конкурентные переводы.

Готово, когда сценарии T01–T07 из `TESTING.md` проходят на PostgreSQL.
Одна `@Transactional` без анализа изоляции и конкурентного доступа не завершает этап.

## Этап 5. Идемпотентность

- [ ] Спроектировать хранение ключей и результатов; добавить ограничения БД.
- [ ] Определить, какие параметры входят в сравнение запросов.
- [ ] Реализовать повтор успешного запроса и конфликт изменённых параметров.
- [ ] Обработать два одновременно пришедших запроса с одним ключом.
- [ ] Проверить повтор после перезапуска приложения.
- [ ] Описать поведение при бизнес-ошибке, аварии и запросе, который ещё выполняется.

Готово, когда I01–I05 проходят, а кэш в памяти не является единственным хранилищем.

## Этап 6. Журнал денег и выписка

- [ ] Спроектировать журнал движений и его связь с переводами.
- [ ] Добавить миграции; решить, как учесть уже существующие остатки.
- [ ] Обновлять журнал вместе с переводом в одной транзакции.
- [ ] Обеспечить сверку баланса и движений, включая начальное финансирование.
- [ ] Сделать выписку с пагинацией и фильтрами периода.
- [ ] Выбрать индексы по реальным запросам; посмотреть `EXPLAIN ANALYZE`.
- [ ] Объяснить, как исправлять операцию, сохраняя историю.

Готово, когда выполнены L01–L04 и по данным можно объяснить происхождение остатка.

## Этап 7. Проект для резюме

- [ ] Подключить Testcontainers и запуск интеграционных тестов в CI.
- [ ] Написать Dockerfile и сборку приложения вместе с PostgreSQL.
- [ ] Описать API через OpenAPI; проверить примеры запросов.
- [ ] Добавить ER-диаграмму и заполненные решения в README.
- [ ] Составить демонстрационный сценарий для двух пользователей.
- [ ] Проверить полный запуск из чистого клона.
- [ ] Заменить описание учебной заготовки в README на фактически реализованные возможности.

Готово, когда другой разработчик запускает проект по инструкции и воспроизводит
успешный перевод, отказ при недостатке денег, безопасный повтор и запрет чужого доступа.

## Дополнительные задания

JWT с обновлением токенов; отмена перевода компенсирующей операцией;
нагрузочный тест; transactional outbox и уведомления. Это расширения,
к которым стоит переходить после завершения этапов 0–7.
