# Задание: внутренний банк

Разработай REST API для клиентов, счетов и переводов между счетами этого же банка.
Используй модульный монолит, Spring Boot и PostgreSQL. Фронтенд не требуется.
Это техническое учебное задание, а не описание требований к настоящему банку.

## Участники

- Гость может зарегистрироваться и пройти аутентификацию.
- Клиент видит собственный профиль, счета и доступную ему историю.
- Администратор может блокировать/разблокировать счета.
- Роль администратора нельзя получить через публичную регистрацию.

## Клиенты и счета

- У каждого пользователя уникальный email для входа; правило нормализации определи сам.
- Пароли не хранятся в открытом виде и не попадают в ответы или логи.
- Клиент может открыть несколько счетов. Начальный баланс нового счёта — ноль.
- Номер счёта уникален. Его формат в этой модели учебный, без имитации реальных реквизитов.
- В первой версии поддерживается только RUB, точность суммы — до двух знаков после запятой.
- Клиент не выбирает владельца нового счёта: он определяется по аутентификации.
- Состояния счёта: `ACTIVE`, `BLOCKED`, `CLOSED`.
- Перевод возможен, только если оба счёта активны.
- Администратор блокирует активный счёт и разблокирует заблокированный.
- Владелец может закрыть только активный счёт с нулевым остатком.
- Закрытый счёт не открывается повторно; история не удаляется.

## Переводы

- Отправитель обязан владеть счётом списания. Получатель может быть другим клиентом.
- Перевод самому себе между разными собственными счетами допустим.
- Перевод на тот же самый счёт запрещён.
- Сумма положительная, не превышает доступный остаток и заданный тобой предел.
- Дробную часть сверх двух знаков отклоняй, не округляй незаметно.
- Овердрафта и комиссий нет. Суммарный баланс участников внутреннего перевода сохраняется.
- Списание, зачисление и запись об успешном переводе атомарны.
- Сбой не должен оставлять половину перевода; параллельные запросы не создают денег.
- Клиент видит перевод, если владеет хотя бы одним из участвующих счетов.
- Ответ не раскрывает email, пароль или иные данные второго клиента.

## Повторные запросы — этап 5

- Ключ идемпотентности обязателен для создания перевода.
- Ключ имеет область уникальности «пользователь + операция».
- Одинаковые ключ и параметры успешного запроса дают тот же результат без нового списания.
- Тот же ключ с другими параметрами приводит к конфликту.
- Два одновременных запроса с одним ключом тоже не создают два перевода.
- Результат переживает перезапуск приложения.
- Политику для отклонённых запросов выбери и документируй отдельно.

## История — этап 6

- У каждого денежного движения есть запись, связь с операцией и время.
- История имеет пагинацию, фильтр по периоду и стабильную сортировку.
- Баланс согласован с журналом движений; проверку этого соответствия нужно автоматизировать.
- В окончательной версии начальные деньги имеют объяснимый источник в журнале.

## Откуда брать деньги для проверки

До этапа 6 используй тестовые фикстуры или локальные dev-данные с положительными остатками.
Не добавляй публичный endpoint, позволяющий любому изменить баланс.
На этапе 6 переделай фикстуры в операции начального финансирования с техническим счётом
или другим явно описанным источником. Обычные клиентские счета не уходят в минус;
правила для технического источника опиши отдельно.

## За границами первой версии

Валютная конвертация, карты, кредиты, реальные платёжные системы, KYC,
восстановление пароля, 2FA, внешние уведомления и распределённые транзакции.
Добавлять их можно после работающего и проверенного основного сценария.
